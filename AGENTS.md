# TB development rules

TB is the primary product. Active code belongs in `frontend/`, `backend/`, `desktop/`, and `server/leaderboard/`.

- 用户界面文案约束（2026-10-26）：未经用户明确要求，不得自行增加界面文字、标签或说明。实现功能时复用既有文案。题单不提供标签功能；操作按钮只显示图标，保留无障碍名称及必要的悬停提示。题目知识点与筛选保留。

- Delivery preference (user instruction 2026-10-24): after validating TB features or teaching updates, package them into the normal desktop program and deliver the local upgrade directly. Do not default to a standalone preview, ask the user to experiment first, or stop with unpackaged source. Do not ask again whether to package. Preserve isolated install/upgrade checks and personal-data backups. This authorizes local delivery, not automatic public publication or service deployment; interactive teaching experiments remain part of Algorithm Lab.

- Read `docs/architecture.md` before changing storage, API boundaries, or packaging.
- Back up existing files before editing. Keep backups outside source directories, in `.backups/`. Verify moved source files by SHA-256.
- Keep the original educational archive and users' live installations read-only during development. Use temporary state for every test. Set `TB_OFFLINE=1` unless a test supplies its own local service.
- SQLite is the persistent storage for library content, personal progress, and settings/cache documents. Markdown is a rendering/interchange format. Never reintroduce filesystem-dependent solution lookup.
- Preserve code, identities, records, API keys, and local imports during migration or upgrade. Back up existing databases with SQLite's online backup API, including committed WAL content. Never replace a personal database with a bundled file.
- Share only public educational data. Distributed content must have no developer progress, credentials, cookies, or absolute machine paths. Translation keys remain protected with DPAPI on Windows.
- Editorial authoring scope (user update 2026-10-22): new or completed editorials are eligible for problem difficulty less than or equal to 2200, including 2200, across all platforms and series, including Lanqiao. Do not add or complete editorials above 2200. Preserve every existing default/detailed editorial, illustration, archive and database entry regardless of difficulty; do not hide or delete them. Apply this limit when planning future work or staging newly authored content, without filtering existing content during packaging or migration. Unknown difficulty requires verification, not an invented low rating. See `docs/editorial-policy.md`; this replaces the 2026-10-19 strict-below-2200 boundary and supersedes broader earlier completion plans.
- Preserve original site login, CSRF, and submit behavior. Compiler adapters act on actual language controls and use native form events. Do not perform account submissions merely to test an adapter.
- API write requests require the session token. Cross-origin access requires an explicit frontend origin; keep the default local-origin guards.
- After backend changes run `python scripts/check.py`. After UI changes run the frontend build and relevant Playwright tests. Run shared-service tests after Worker changes. Packaging requires fresh-install and upgrade checks against disposable state.
- Every release must synchronize its actual source, `VERSION`, frontend/extension versions, both READMEs, affected usage/development/site documentation, and release notes in the same release preparation. Verify features, public-library counts, download filenames/links, and migration instructions against that version. Push the source and documentation before publishing assets; the release tag and `BUILD-INFO.json` must identify the commit used to build them. Never publish binaries alone while leaving GitHub source or READMEs behind. When source is ahead of the latest stable release, label both versions and the unpublished status explicitly; download links must continue to point to published assets. Follow the checklist in `docs/development.md`.
- Every version or PR update must also be visible in the user's designated local project directory. Maintain one current update record with commit, status, validation, source location, and actual startup entry. Keep only the latest complete runnable program and files required for active development; do not archive historical executables, release packages, duplicate source snapshots, or old build directories. Before cleanup, verify source is saved on GitHub and preserve any unpushed changes and personal data. Validate a replacement in isolated state, migrate personal data after the old program closes, then update the latest shortcut and remove the superseded program. Clearly identify unpackaged updates and pending PRs.
- Report actual checks and limitations. Never claim real official submission or provider success from a fixture. Do not publish releases, deploy services, or merge a PR unless authorized in the conversation.

## Teaching content

- Apply `docs/algorithm-lab-authoring.md` as the persistent end-to-end workflow for algorithm lessons, five curated guided problems, independent implementation handoff, related detailed-editorial revisions, validation and release. Use meaningful interactions beyond reveal-only hints; keep necessary reasoning concise and visible.
- Related detailed editorials must explain problem-specific recognition, changes from the basic algorithm and useful debugging/transfer cases where they help. Audit actual relevance and difficulty, preserve existing content, and never append identical boilerplate across problems.
- Follow the basic teaching-writing standards and recorded lessons in `docs/algorithm-lab-design.md` for every algorithm lesson or teaching revision.
- State the current problem and explain concrete choices before introducing symbols. Distinguish allowed choices, processing order, actual actions and final results; never rely on the reader inferring these distinctions.
- Keep the example, visual state, formulas and explanations synchronized. Review likely novice misreadings explicitly; correct output and UI tests alone do not establish clarity. Concision removes repetition, not necessary reasoning steps.

- Editorial teaching revision (user feedback 2026-10-22): apply `docs/editorial-teaching-standard.md` to all existing and future editorials. Explain language/library tools as independent, reusable from-zero lessons; include boundary-function implementation/complexity and lambda capture/lifetime guidance. Draw the actual mathematical objects when explaining spatial or set-subtraction formulas. Preserve verified reference programs and all existing educational content.

- 用户发行要求（2026-10-22）：管理员版本仅供维护者本机自用，禁止上传 GitHub（含草稿、正式版、便携包、安装包、管理员清单及公开校验索引）。公开发布只含用户版；管理员产物必须位于 `stage/private-admin`，与公开 `stage/release` 分离，上传前使用 `scripts/release_assets.py` 校验。保留本机管理员程序及个人数据。

- Local desktop packaging authorization (2026-10-22): the user explicitly requests packaging Algorithm Lab into the normal desktop program. Build the completed, committed course in the isolated 1.3.6 branch and validate local installation/upgrade while the separate editorial review continues. This authorizes local program delivery, not public release, service deployment or a claim that all editorials have been reviewed.
